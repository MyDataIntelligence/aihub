# aihub 1.0.4

## Wat is nieuw
- Fix vanuit de melding: `aihub watch --mine` volgt ook je eigen builds. Faalt een build op je eigen featurebranch (nooit main, staging of release), dan krijgt de melding een knop Fix. Die opent de chat met de agent `aihub` en `/fix <run-url>` (opencode en Claude Code via `--agent aihub`, Codex en Copilot zonder agentkeuze).
- Nieuw commando `/fix` en vernieuwde skill `pipeline-fix`: `aihub pipeline logs --failed [--run <id|url>]` (zonder run: de nieuwste mislukte run van de branch) toont eerst de branch, of die beschermd is en hoeveel runs op rij rood zijn, daarna de mislukte stappen. De agent stopt bij een beschermde branch en na drie rode rondes; flaky of infrastructuurfouten worden gemeld en niet "gefixt". Werkt zonder story.
- `aihub pr data-diff [--pr N] [--write] [--baseline W] [--feature W] [--json]`: voert dezelfde alleen-lezen controles uit in de baseline-workspace (waar de doelbranch draait) en de feature-workspace van de branch en toont een tabel vóór/na met verschillen en een oordeel van één regel. Controles per tabel in `team.yaml` onder `dataChecks:` (aantal, nulls, som, distinct, of een eigen SELECT). Via het SQL-endpoint (`fabric sql`), met Livy als terugval; het zegt welke is gebruikt. ACC en PRD worden geweigerd. `--write` zet de tabel in de PR-sectie "Data vóór/na" ("Data before/after" bij een Engels team), net als Wijzigingen door de code gevuld. De skills pr-create en pr-update roepen het aan als `dataChecks` bestaat.
- Voor-review van andermans PR: `aihub review prepare --pr N` (diff met regelnummers, threads en het bestand voor de bevindingen) en `aihub review post --pr N --pick 1,3,5` (alleen de gekozen bevindingen als thread op de juiste regel, met `[ernst]` en suggestie). Zonder `--pick` wordt er niets gepost; een onbekend nummer plaatst niets. De skill `pr-review` schrijft genummerde bevindingen en toont ze eerst.
- `aihub release plan --from DEV --to ACC [--target <branch>] [--out plan.yaml] [--notes-out notes.md] [--json]`: wat gaat er van de ene omgeving naar de volgende (alleen lezen). Git (`origin/<ACC-branch>..origin/<DEV-branch>`) laat zien welke Fabric-items zijn gewijzigd en via welke PR's en stories; de stage-items van de deployment pipeline laten zien welke items nieuw of verwijderd zijn. Per item de status, PR's en stories, de cherry-picklijst in merge-volgorde en release-notes in de teamtaal; `--out` schrijft een plan voor `aihub release run`. Instellen met `fabric.environments` (branch en stage per omgeving) en `fabric.deploymentPipeline` in team.yaml; zonder pipeline of bij een Fabric-fout is het plan git-only en zegt dat. Deployen blijft het beveiligde `aihub fabric deployment deploy`.
- `aihub fabric sql` op het SQL-endpoint van een lakehouse loopt weer native (tedious 19.2, token voor `https://database.windows.net/` met slash; de .NET-terugval op Windows blijft als vangnet), en `--item <lakehouse>` is niet meer "ambiguous" met het gelijknamige SQL-endpoint. `aihub fabric spark stop` stopt een sessie nu echt (de echte API noemt het item in `item.itemId` en schrijft het type met kleine letters; live was het item-id `undefined`), en `--all-mine` neemt alleen sessies van de ingelogde identiteit. De minimale Node-versie is 18.17.
- `aihub standup [--since yesterday|today|<duur>]`: 3 tot 5 regels uit je commits, PR's (aangemaakt, gemerged, bijgewerkt), reviews waarop je reageerde, builds en statuswijzigingen van stories (op maandag is `yesterday` vrijdag). `aihub handoff [--to <naam>] [--clipboard] [--wiki]`: je openstaande werk als korte markdownnotitie (open PR's met stemmen, threads en build, stories, niet gepushte branches, lopende watches, falende runs). Beide lezen alleen, in de teamtaal uit team.yaml; `--wiki` is de enige schrijfactie en alleen op verzoek. Nieuwe skill `standup` met `/standup` en `/handoff`.
- Foutgeheugen: `aihub fix known [--run <id|link> | --error "<tekst>"]` zoekt de fout op in `known-fixes.md` van het teampakket (zonder cijfers, id's en paden in de vergelijking); `aihub fix remember --error "<regel>" --fix "<1-3 regels>"` stelt een nieuwe regel voor als pull request, vanuit een tijdelijke worktree (niets gaat stilzwijgend op, je checkout blijft ongemoeid). De skill pipeline-fix vraagt eerst `fix known`. `aihub team learn "<regel>"` stelt een teamregel voor op dezelfde manier. `aihub crossrepo impact --from <pr|sha>` laat zien welke bestanden via `crossRepo.pathMaps` in andere repositories terechtkomen en welke daar al bestaan (alleen lezen).

- `aihub watch --run <id|link> | --robot <build> | --fabric-job <workspace/item/job-id> [--notify]`: volgt één lange run op de achtergrond (losgekoppeld zoals `watch --mine`) en meldt het resultaat, met de Fix-knop (`/fix ...` voor de agent `aihub`) als hij op een featurebranch faalde. De skills pipeline-fix, fabric, test-run en story-run zeggen nu "ik volg het op de achtergrond" in plaats van te blokkeren op `--wait` of `pipeline follow` (die blijven voor wie erom vraagt).
- Hulpjes voor een PR volgens de gouden standaard: `aihub pr comment --closed --title "…" [--link-section Resultaat]` zet een detailcomment als gesloten thread en voegt "Details: [titel](…?_a=overview&discussionId=N)" toe aan die sectie; `aihub pr tests add --from-run <id> | --from-robot <id> | --from-fabric-job <ws>/<item>/<job>` voegt een eerlijke rij toe aan de testtabel uit de echte run (naam, resultaat, link, duur; een lopende run wordt geweigerd; dezelfde run wordt ververst, niet dubbel); en `pullRequest.afterCreate: {storyState, autoComplete}` in team.yaml, uitgevoerd door `pr create` direct na een nieuwe PR. Auto-complete wordt alleen gevraagd als de doelbranch een blokkerende policy heeft (anders zou de PR meteen worden samengevoegd) en omzeilt nooit een policy; een fout wordt gemeld, de PR blijft.
- Azure DevOps testplannen en artifacts: `aihub testplan plans|suites|cases|points|outcome|runs|results|create-plan|create-suite|create-case` en `aihub artifacts feeds|packages|versions` (alleen lezen). Nieuwe skill `devops-boards` voor werkitems, bord, testplannen en artifacts.
- De opencode-agents `aihub` en `aihub-runner` staan standaard op toestaan (opdrachten, bewerkingen, lezen, web) en weigeren alleen een korte gevarenlijst (force push, direct pushen naar main/master/staging/release, `rm -rf /*`, `az ... delete`, `curl | sh`); `aihub-researcher` blijft alleen-lezen. `aihub skills install` toont de bijbehorende auto-approve-instellingen voor Copilot/VS Code, Codex en Claude Code. Elke aihub-agent zegt: nooit de oude `hub`-CLI gebruiken; `aihub doctor` meldt `legacy-hub` en `aihub skills install` waarschuwt, met `aihub legacy remove --dry-run`.

- dbt-ondersteuning: `aihub dbt detect|check` (project, adapter, versies, installatieproblemen) en alle dbt-verbs op de lokale dbt (`build`, `run`, `test`, `compile`, `seed`, `snapshot`, `show`, `ls`, `deps`, `debug`, `parse`, `retry`, `freshness`, `docs`, `run-operation`) met selectors, `--state`/`--defer`, compacte uitvoer en `--json`. Schrijfacties op een Fabric-adapter lopen via `aihub fabric dbt run --workspace`.
- `aihub dbt failures`: mislukte test of model met melding, gecompileerde SQL en de eerste falende rijen; `aihub dbt lineage <model>`.
- `aihub dbt impact [--base] [--state <map>|auto] [--write]`: gewijzigde modellen, downstream modellen, tests, exposures en Fabric-items; `--write` zet een door de code beheerde sectie "dbt impact" in de PR. Met `--state` vergelijkt dbt LF-kopieen van beide kanten, dus autocrlf op Windows geeft geen valse wijzigingen.
- `aihub test changed` plant dbt-builds voor gewijzigde modellen (`tests.dbt` in team.yaml: `command`, `mode`, `state`).
- `aihub dbt yaml check|scaffold`: ontbrekende entries, beschrijvingen en tests, verouderde `tests:`; scaffold schrijft een modelentry of unit-test-skelet (alleen typen, nooit echte waarden).
- Nieuwe skill `dbt` met naslag; implement, pr-create en test-run verwijzen ernaar.
- Learn 2.0 (persoonlijk): `aihub learn change|repo|validate|save|list|show|forget|concepts|quiz`, skill `learn` en `/leer` (uitleg met Mermaid-diagrammen eerst), en in de VS Code-extensie de Learn-view, een lespagina en een rondleiding. Alles blijft in ~/.config/aihub/learn, niets in de repo.
- Onderzoeksmodus: `/kan-dit` en `/can-it` (skill `feasibility`, subagent `aihub-researcher`), `aihub probe fabric|devops|api` (alleen lezen) en `aihub research template|save`; elk rapport bevat "Waar hoort het: Fabric, DevOps/CI-CD of beide?" met één adviesregel.

## Context
Een rode build op je eigen branch is het vaakst voorkomende werk dat je niet wilt zoeken: de melding zegt het, één klik start de oplossing, de agent volgt de herstart.

Een PR die data raakt, liet alleen code zien. Reviewers willen weten wat er met de cijfers gebeurt.

Elke ochtend en bij elke overdracht schrijf je op wat er gebeurd is; de gegevens staan al in Azure DevOps en git.

Een review die de agent voorbereidt maar jij beoordeelt: jij kiest wat er onder jouw naam op de PR komt.

Dezelfde fout wordt in elk team steeds opnieuw opgelost; het teampakket onthoudt het, via een PR die een mens samenvoegt.

Een agent die tien minuten op een build wacht, blokkeert jouw sessie en verbruikt tokens; de melding doet hetzelfde werk.

Testresultaten van een build en de testplannen waren alleen in het portaal te zien.

Op een werklaptop liep de nieuwe agent toch `hub call ...` (de oude Hub won) en vroeg bij elk opdrachtje om toestemming.

## Compatibiliteit
Geen brekende wijzigingen. `aihub pipeline logs --run` accepteert nu ook een build-link. De Fix-knop werkt zodra `aihub watch --mine --notify` draait en de `aihub://`-handler geregistreerd is (zoals bij de Open-knop). Fabric-runs geven nog geen eigen melding: gebruik `aihub fabric failures`.

Geen brekende wijzigingen. Zonder `dataChecks` verandert er niets.

Geen brekende wijzigingen. Een deel dat niet leesbaar is (geen toegang tot een repository of builds) valt weg uit het overzicht. Fabric-runs zijn nog geen onderdeel; de builds wel.

`aihub review post --comments-file` werkt zoals voorheen. `review post` zonder bestand leest de bevindingen uit `<git common dir>/aihub/review/pr-<N>.yaml` (lokaal, nooit gecommit).

Geen brekende wijzigingen. `known-fixes.md` en `team-knowledge.md` ontstaan pas bij de eerste voorgestelde regel; `fix known` leest het bestand van de doelbranch (`origin/<target>`), anders de werkmap.

`--wait` en `pipeline follow` werken zoals voorheen. `aihub watch list` toont de gevolgde runs en `aihub watch stop` stopt ze.

Geen brekende wijzigingen. Voor testplannen heeft het account de Test Plans-licentie nodig (anders 403); `testplan runs|results` werken zonder.

Wie de agentbestanden zelf bewerkte, houdt ze (checksum-regel); `aihub skills update` ververst de onbewerkte. De 2.x-permissielijst volgt dezelfde regels maar is niet op opencode 2.x gedraaid.
