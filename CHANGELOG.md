# Changelog

One `## <version>` heading per release, one bullet per change. `aihub update` shows the bullets between the old and the new version.

## 1.10.0

- Team settings: `aihub team show --json` gives the whole Team settings page in one read (which team.yaml applies, every key per repository with its explanation, overrides, templates); `team validate` (errors with line and fix), `team preview --template pr|story|bug|commit`, `team edit` (a new branch and a pull request in the team repository, never main) and `team init --from-pack | --team-repo`. Repositories without their own team.yaml use the team repository once one is set. The schema documents `teamName`, `worktrees`, more `workItems` keys and two Fabric keys.
- Run End to End: team prompts with `/story-*` and `/bug-*` commands, acceptance criteria with how tested and proof and a status per criterion, the criteria section in the PR, run progress, YOLO with fixed limits, and the bar bridge; a Bug has no acceptance criteria.
- `browse file` never downloads a binary or a file over 5 MB; folder sizes; text search without Code Search in the clones on this PC.
- `aihub browse change`: Change with Agent without a clone (a workspace per change, diff, push as one commit on a new branch with a PR, fixed limits).
- `browse search --scope` over several projects and repositories; `aihub browse ask` (a read-only question over that scope, counted reads, proposals, apply as changes on one branch name); `browse related` (the tests and users of a file).
- `aihub branch update` works with any git remote, names the target and why, says "already up to date with <target>", and hints `--target staging` when another target was chosen.
- A feature branch cut from staging keeps staging as its derived target, also when main was on the same commit or was merged into it.
- Stories: the board column per item, a count per column, the total of a list, and the team's areas when the saved area is the project root.

## 1.6.0
- `aihub branch switch --repo <r> --branch <X>`: one repository of the set you are in on another branch, in its own worktree (`git switch`); the folder, the workspace file and the other repositories stay and no window opens (`the window stays as it is: 3 repositories, repo-b now on X`). `worktree open --repos` with only some repositories of the set does the same; `--new-set` still makes a new set. Uncommitted work: nothing switches and the line gives the choices.
- The CLI reads and writes the sets of the VS Code extension too (`.worktree-set.json`, schema 1, nothing renamed): `status`, `--all-repos`, `worktree list`, `branch switch` and `worktree add|drop|repair` work in them, and a switch updates that file and its workspace folder names, so the Worktree Sets view stays right.
- A repository of a set can have its own branch: optional `repos[].branch` in both set files (older files stay valid); `worktree open|create --branch-for repo-b=<branch>`; `status` (`set.branches`), `worktree list`, `resume` and the `--all-repos` table show it.
- `aihub worktree add --repos d [--branch X]`, `worktree drop --repos d` (uncommitted or unpushed work keeps the worktree, and it is reported) and `worktree repair` (the worktree of a repository added to the set file by hand, also with only a name; `status` names such entries). The set file and the workspace file are updated in one go; the window stays.
- A branch whose worktree already exists elsewhere: `worktree create|open|add|repair`, `story open` and `branch switch` stop before anything changes with one question line and three ready commands (exit code 3; `--json`: `needsChoice`): `--existing move` (recommended: `git worktree move` into the set, work goes along, checked and put back when it went half), `--existing reuse` (as before) or `--existing recreate` (the old worktree removed, folder links first; uncommitted work only with `--discard-local-work`, after a patch backup under `<git dir>/aihub/backup/`). No question when it is already in the set, in the main clone, or a registration without a folder (pruned). Personal preference: `aihub worktree when-exists ask|move|reuse|recreate`. Skill `worktrees`: one question, or the choice the user already said. Release notes: docs/releases/1.6.0.md.

## 1.5.0
- `aihub commit`: a git hook that stops the commit or the push is explained: which hook, the failed checks (pre-commit table, or the error lines of any other hook), their first lines, the files the hook changed itself, and the full output in `<git dir>/aihub/last-hook-output.txt`. The choices are printed as commands: fix and run again, `--skip-hooks <ids>` (new, the pre-commit hook ids) or `--no-verify`. Hooks that only reformatted files get one automatic second try. After a pre-push failure the commit stays; the same command again only pushes.
- Red pipeline runs are facts, not an order to stop: `pipeline logs --failed` no longer prints `STOP after 3 red rounds`, the skills `pipeline-fix` and `story-run` no longer refuse on a count, and the agent text says the user's "ga door" or "override" beats any stop rule. Still refused: force-push, a direct push to a protected branch, ACC/PRD. `--json`: `stop` is replaced by `note`.

- Fabric: `fabric logs --job` prints a digest (failed cell, exception, likely cause, error excerpt) instead of the whole log; `run --wait` and `status --wait` end with the cause; new `item edit`; `git commit --message` or no message; `failures --item`; a missing driver log is read a second way and never hides the cause; `fabric help` is one short screen.
- Agents and skills: long jobs run in the main chat (the runner only on request); aihub is on the PATH, an unreadable skill file means `aihub <command> --help`; done is done, no closing question; do not read team.yaml. Release notes: docs/releases/1.4.0.md.

- `aihub legacy remove [--yes] [--keep-data] [--keep-settings] [--repos <dir>]`: lists, then removes, everything the old AI Context Hub put on the machine (extension below 3.0.0, `hub` CLI package and PATH entry, its skills, agent, rules block and hooks, data, per-repo `.aihub`, exclude lines and git hook blocks); only what is provably Hub-owned, your own files and hooks stay. See docs/legacy-removal.md.
- `aihub init` also proposes `.github/instructions/<area>.instructions.md` skeletons (`applyTo:` front matter, empty rule bullets, for the file types the repository really has) and a marked aihub block in `AGENTS.md` (created, or appended only when the file has no aihub line); each only when missing. `--no-instructions` and `--no-agents-md` skip them.
- `aihub comments reply --reply "<threadId>:<status>:<text>"` (repeatable, no file needed; an agent whose shell may not write files can still answer threads) and a value that starts with `- ` (a markdown bullet, for example `--append-text "- item"`) is accepted after its option.

Release notes: docs/releases/1.0.3.md.

## 0.1.0
- `aihub pr create|update`, `comments get|reply`, `story`, `branch`, `cherry-pick`, `pipeline`, `batch`, `work`, `fabric`, `robot` and the other workflow commands.
- `aihub init` proposes team.yaml and the templates as a pull request; it never overwrites a file.
- `aihub skills install|update|diff|uninstall` copies the bundled skills and slash commands into opencode, Codex and Copilot.
- `aihub doctor` checks sign-in, remote, team.yaml, PR template, guideline files and the installed skills.
- `aihub update [--check]` updates the CLI and the skills; `aihub explain <command>` describes a command step by step.
- `--dry-run` prints the writes (git and REST) a command would do; `--verbose` logs the real calls.
- One-line installers (install.ps1, install.sh, Install-aihub.cmd), docs/self-hosting.md and azure-pipelines.yml for teams that run aihub from their own feed.
- `team-pack/`: the copy-ready team files (also the source of `aihub init`), attached to each GitHub release as aihub-team-pack-<version>.zip.
- guidelines: in team.yaml: repository files the agent reads first.
